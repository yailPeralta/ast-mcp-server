# ADR 0015: DeepSeek Harness Developer Preview adapter — first slice

## Status

Accepted.

## Context

The macro roadmap (initiative 4) validates DeepSeek Harness Developer Preview interoperability through the official `@deepseek-ai/dsh-mcp-client` bridge over stdio, pinned to Harness `dsh-v0.1.2-alpha.1` at revision `cd5ef8148158c3a752a658978873241fdf8e2bbc`. Harness does not resolve MCP binaries from `PATH`, and the official bridge drops MCP tool `annotations` (including `readOnlyHint` and `destructiveHint`) and launches the stdio child outside the Harness sandbox. The first supported surface is therefore reads + prepare + preview, with every apply path denied by a fail-closed guard.

Two pinned identities are not published to npm as-is: `@deepseek-ai/dsh-mcp-client@0.1.2-alpha.1` and the `@deepseek-ai/dsh` CLI at that version. The adapter therefore records the pinned identity tuple in the separate top-level `deepseekHarness` compatibility field, keeping the loader-owned `dsh` object exact. The mandatory smoke resolves the bridge from the pinned source (a clean checkout at `cd5ef814…`, source-built) rather than accepting any ambient `dsh` or a wrong-version npm package.

## Decision

Ship a thin adapter inside the `ast-mcp-server` package (target `0.13.0`), not as a separate package:

- `package.json` declares exactly `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`, ships `cordis.patch.yml` in `files`, and records `deepseekHarness` (`revision` `cd5ef814…`, `tag` `dsh-v0.1.2-alpha.1`, `mcpClientVersion` `0.1.2-alpha.1`) outside that exact loader contract. The adapter declares no `@deepseek-ai/dsh-mcp-client` npm dependency: the pinned bridge is supplied and pinned explicitly by the smoke.
- `cordis.patch.yml` inserts one `@deepseek-ai/dsh-mcp-client` row (`serverName: ast`, `transport: stdio`, `failOnStartupError: true`) whose entrypoint resolves package-relatively: `command: !!js process.execPath` and `args: [!!js fileURLToPath(new URL('node_modules/ast-mcp-server/dist/index.js', baseUrl))]`, where `baseUrl` is the profile directory file URL available to loader `!!js` expressions. This avoids ambient `PATH` resolution and works from the packed tarball.
- The row sets `env: { AST_MCP_APPLY_GUARD: 'deny' }`. The server parses a closed, fail-closed guard vocabulary: only an explicit `allow` registers the `effect: "apply"` tool (`ast_apply_operation`); `deny`, an unset value, or any invalid value denies it at registration. Ambient agent surfaces (Codex, Hermes, Claude Code, Gemini, Copilot, OpenCode) opt back in through a per-server env (`AST_MCP_APPLY_GUARD=allow`) that `ast-tool setup` writes into each MCP registration.
- `yarn test:dsh-adapter` is mandatory and never green-skips. Phase A proves the tarball fixture, exact loader metadata, and tarball hash; phase B runs the full guard matrix (unset/deny/invalid → 15 tools, `allow` → 16) plus a read/prepare/preview flow at the resolved entrypoint; phase C resolves the pinned harness (HARD FAIL on a dirty/missing source or revision/tag/version mismatch), installs the exact tarball into an isolated profile, proves effective `tools.mode: native`, and invokes the server-qualified read, dry-run rename, and preview tools through the Harness registry. It proves apply absence and a bounded rejected direct apply invocation separately.

## Evidence boundary

- `yarn test:dsh-adapter` passed all three phases against the source-built pinned harness: tarball fixture, guard matrix, independent read/prepare/preview flow, profile install + native `--dump-config` composition, and Harness-mediated server-qualified read/prepare/preview invocations with apply absent and rejected.
- The smoke verifies the pinned identity tuple (`git rev-parse HEAD == cd5ef814…`, clean worktree, tag resolves to HEAD, CLI `--version == 0.1.2-alpha.1`, mcp-client `0.1.2-alpha.1`) and records CLI/client tarball/package tarball SHA-256 values before any Harness-mediated claim.
- These are Developer Preview results: no compatibility promise, no `apply` claim, no `ptc`/Code Mode claim, and no `dsh plugin add ast-mcp-server@<version>` registry promise (0.13.0 is not published; the smoke uses a packed tarball).

## Consequences

- The Harness surface exposes only reads, prepare, and preview; `ast_apply_operation` is denied for unset, `deny`, and invalid guard values and enabled only by an explicit `allow`.
- Annotations are dropped by the bridge and the stdio child runs unsandboxed; these gaps are documented and never used as safety authority.
- Ambient agents require an explicit `allow` env in their MCP registration, generated by `ast-tool setup`.
- A later `apply` claim requires explicit proof of root/session binding, review/hash binding, explicit approval, workspace-change rejection, reconnect/restart/HMR/expiry behavior, and zero cross-workspace authorization.
